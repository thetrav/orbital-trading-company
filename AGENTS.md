# Agent instructions

## Validation

After every batch of changes, run `./validate.sh` and verify all 6 checks pass before reporting done. The script runs `luacheck`, `lua-language-server`, `busted`, `--dump-data`, `--create`, and `--load-game --until-tick 600`.

Do not skip this step. Do not rely only on headless Factorio — also check `luacheck` and `lua-language-server` output for regressions.

`validate.sh` prints its own pass/fail summary — read that rather than piping it through `grep`/`head`. If you need different output, change the script (flags or env vars are fine).

## Probing the real game

`tools/probe.sh <probe.lua> [--ref <git-ref>] [--ticks N]` runs a throwaway module inside headless
Factorio and prints anything it `log()`s containing `PROBE`. Use it for behaviour that only the
real API can answer — entity status, power, what a drill bound to. `--ref` stages a git ref
instead of the working tree, which makes an A/B against unmodified code one command. The mod is
staged into a temp directory, so the repo is never touched and there is no wiring to remember to
remove. Probes live in `tools/probes/`. A crash prints its stack trace on the lines *after* the
"Error while running" line, which the default filter drops — rerun with `PROBE_VERBOSE=1` to see it.

**`on_nth_tick` also fires at tick 0 when a save loads.** A probe that reports on the first firing
measures a world that has not run a single tick: everything reads `no_power`, no drill has a
mining target, and no assembler has started. Guard with `if game.tick == 0 then return end`.

## Tests

`test/` holds [busted](https://lunarmodules.github.io/busted/) specs, run by `validate.sh` step 3 and configured by `.busted`. Install with `luarocks install --local busted`; the step takes busted from `$BUSTED`, else from `PATH`, else from `~/.luarocks/bin`. When it is missing entirely it falls back to `test/minimal_runner.lua`, a cut-down runner that covers the describe/it/assert subset these specs use, so the suite still runs on a plain `lua` — write specs against busted's API, not the fallback's.

`factorio_mock.gui_root()` returns a stand-in for `LuaGuiElement` (children reachable by name, `children` handing back a copy, style fields writable), which is what lets a GUI module be built and driven in a spec rather than only in game.

`test/factorio_mock.lua` stands up the runtime globals (`game`, `storage`, `prototypes`, `defines`) that a module under test reads — `mock.setup{...}` takes a technology-name → spec table and wires prerequisites by name. Call `mock.teardown()` in `after_each`, and clear `package.loaded` for the module under test before requiring it so each spec gets fresh state.

Prefer adding a spec here over ad-hoc probe scripts that get `require`d from `control.lua` — those need a headless round trip and leave the repo dirty. When only the real API can answer the question, use `tools/probe.sh` rather than hand-wiring one. `test/` is excluded from `lua-language-server` via `workspace.ignoreDir`, because the mock's globals otherwise shadow the real API stubs and produce false `undefined-field` reports.

## What this mod is

Factorio 2.0 mod "Orbital Trading Company" (`info.json`, version 0.1.0, depends on `factorio-charts >= 1.0.0`). Players spawn on a 10x10 floating platform on a resource-free Nauvis, join or create a **company** (implemented as a Factorio force), and expand a network of interlinked platform "rooms" (hubs, corridors, factories, orbital stations, asteroid mines, water pumps). A company's orbital trading silo buys and sells against a shared credit economy; a dynamic market prices items and reacts to supply and demand.

## Code layout

- `data.lua` — loads every file in `prototypes/`.
- `data-updates.lua` — gives the `out-of-map` tile a probability-1 autoplace. This is what makes **orbital station surfaces void**: `orbital_station.lua` asks for a surface whose only tile autoplace is `out-of-map`, and a tile with no autoplace specification cannot be asked for. It is global and unconditional, which is why Nauvis has to opt out explicitly (below).
- `data-final-fixes.lua` — Nauvis generates as a **normal world** (terrain, water, cliffs, trees, rocks, decoratives all kept). It removes exactly two things: every resource — ore, stone and oil — and enemies. Resources are dropped out of Nauvis's `autoplace_settings.entity.settings` **and** their `autoplace_controls` zeroed, because a named entry is placed whatever the control says; the resource *prototypes* keep their autoplace specs, since the planet's setup errors without them. It also sets Nauvis's tile `treat_missing_as_default = false`, without which `data-updates.lua`'s global out-of-map fallback wins and the whole planet comes out void. Also: rocket silo uses void energy.
- `control.lua` — all event wiring (init/load, ticks, GUI, built/mined/died, teleporters). Per-tick logic runs on `on_nth_tick(1)`; history + trading GUI refresh on `on_nth_tick(60)`.
- `scripts/` — runtime modules (see below).
- `prototypes/` — one file per entity/item; several deepcopy base prototypes (gate control, company monitor, teleporter, water pump).
- `types.lua` — lua-language-server stubs (partial classes, `remote.call`).
- `doc/` — design backlog (`design-thinking.md`) and plans. Read before starting economy/expansion work.
- `scripts/shapes/` — **captured** shape definitions (data, not code), one file per shape, plus the procedural `connector.lua`. Do not hand-write geometry here; capture it in game. Importing a capture is three steps: copy it out of `script-output/otc-shapes/`, add a line to `shape_registry.lua`, and paste back any `hook =` line (see the gotcha — capture never emits one). See README.md "Capturing shapes".
- `scripts/shape_hooks/` — per-shape post-apply behaviour, registered in `init.lua`.
- `tools/` — one-off migration harness (`export_builtin_shapes.lua`) and the pre-capture generators it renders (`legacy_shapes/`). Excluded from lua-language-server via `workspace.ignoreDir`.

## Runtime module map (`scripts/`)

- `trading_silo.lua` — the whole trading mechanism, model and simulation only. A company's orbital `otc-trading-silo` holds ordered buy and sell lists; a buy order is a **quantity to maintain** (bought at `floor(price * 1.01 + 0.5)`), a sell order ships **everything** of that type (at `* 0.99`). An item is never on both lists. `resolve()` returns the orders in force this tick — the stored lists, or, when circuit control is on, the wires instead: a positive signal is a buy target, a negative one sells all, zero is ignored. `process()` runs every tick and buys as much as the tightest of credits, Nauvis stock and free slots allows, in list order.
- `trading_silo_gui.lua` — the order panel: buy and sell lists side by side, the circuit checkbox and its wire selector. It lives in `player.gui.relative` **anchored to the silo's own container window**, not in `gui.screen`, so the vanilla inventory GUI is left completely alone. View only; every mutation goes through `trading_silo`.
- `pricing.lua` — BFS through tech tree computing a static base price per item (raw resources = 100; recipe cost = ingredients + smelting fuel + `energy * 10`/s). Runs on init/load into `storage.prices`. This is now only the **anchor**; the traded price is the anchor scaled by Nauvis's stock level.
- `stock.lua` — Nauvis's finite warehouse, `storage.stock.items[item] = count`. `TARGET_STOCK = 1000`, `SCARCITY_CAP = 20`. `scarcity()` returns `(T/s)^0.7` below target and `(T/s)^2` above, so prices climb as shelves empty and collapse when flooded. The warehouse starts **empty** and nothing is ever seeded: an item with no entry reads as 0 — `TARGET_STOCK` is what Nauvis *wants* to hold, not what it starts with — so a new game begins with everything at the scarcity cap and Nauvis holding only what it mined, made or was sold. `take` never returns more than is held, which means Nauvis cannot sell what nobody has supplied; the `nauvis_start` shape's four mine blocks are the only thing that breaks that deadlock at the start of a game. `items()` exposes the raw table for listings.
- `supply_demand.lua` — 10-tick periods aggregate buys/sells; `price_offsets[item]` drift by `demand * 0.01`, decay `* 0.95`. Applied to the anchor *before* the scarcity multiple. Now partly redundant with stock movement — see `doc/nauvis_economy.md` §1.
- `utils.lua` — `format_number` (comma thousands), `get_base_price`, `get_price` (`(base + offset) * scarcity`, floored at 1 and capped at `base * 20`), `get_stock`.
- `supply_belts.lua` — per-tick processing for Nauvis's two physical stock interfaces. Supply: pushes one item per lane per tick from stock onto a registered belt, stopping when stock runs out; lane 1 takes `left`, lane 2 takes `right`, and a nil lane is skipped so it stays clear for something else to load. `register_from_def` resolves a shape entity's `item` / `item_left` / `item_right` onto those two lanes. Intake: drains every transport line into stock.
- `research.lua` — Nauvis's research monopoly. Instantly researches the three craft-item trigger techs (`steam-power`, `electronics`, `automation-science-pack`) on init, replays every Nauvis technology onto all other forces, and disables every recipe producing a `tool`-type item or a lab. `ensure_research` auto-queues the cheapest technology whose ingredients Nauvis can actually make (currently red science only). `block_lab` destroys and refunds labs built by non-Nauvis forces.
- `voting.lua` — Nauvis's governance. One ballot per `kind` (`mayor`, `research`, `expansion`), each running for one day/night cycle (`surface.ticks_per_day`), announced on open and again a minute before close. A **bond** is a vote (`storage.nauvis.bonds`) — company shares govern a company, bonds govern the state. First past the post; ties, and a ballot nobody voted in, are drawn with `math.random` from the tied options. `decided_early` closes a ballot the moment no outstanding bond could change the result. `KINDS` holds each kind's title, its option provider and its one-line `resolve` — adding a votable decision is one entry there plus a GUI section. See the gotchas below for why research and expansion ballots open themselves.
- `nauvis_expansion.lua` — the public works builder. `M.OPTIONS` is the ballot put to `voting.lua` (solar field, four mine blocks, automation science, lab district), each naming an already-captured shape. `cost(key)` derives the bill of materials from that shape's entities via `items_to_place_this`, so recapturing a shape retunes its price and nothing has to be kept in sync by hand. `set_target(key)` is what the ballot calls; it refunds any set-aside goods the new target does not need. `process()` runs once a second: draw **surplus only** (`stock.get(item) - stock.TARGET_STOCK`) into `progress`, and once every line is covered hand the shape to `nauvis_siting.request` rather than building it. It also polls `siting.take_completed()` and books the finished build (`finish`), which is what clears `target` and reopens the ballot. It no longer places anything itself.
- `nauvis_siting.lua` — everything otc builds on Nauvis after the compound is placed **by hand**, and this is the queue. Requests are keyed by **client**: `"nauvis"` is the state's own public works, `"company:<force>"` is a company's facilities, and each queue drains independently so one waiting on a mayor never blocks another. A request sits in `storage.nauvis_siting.requests[client]` until someone opens a company monitor and clicks "Choose a site", which puts the shape's footprint in their cursor (the same `otc-place-*` item the dev placer uses, so the build preview and the reach bonus are handled in one place). `validate(surface, box)` is the whole rule set and is the *same* for both, and it is now down to **two rules**: no water in the footprint, and nothing already built in it. Nothing else — not distance from the rest of the world, not proximity to enemies. Trees, rocks, cliffs and fish are not obstacles either, because `platform.place_shape` levels them. `place(surface, origin, client)` is the player-free half (validate, border, build, chart) so probes can drive it. `take_completed(client)` hands the result to whoever made the request, which is what keeps this module ignorant of expansions and companies alike.
- `district.lua` — the module grid, its two zones, the grass a module is laid on, the big-pole power line and the concrete path it stands on. **`build()` currently has no callers**: fixtures are gone and a company's facilities are sited by hand, so everything that used to pack into the grid now goes through `nauvis_siting`. What is still live is `init` / `chart` / `chart_all`; `ensure_pole` lost its last caller when siting stopped laying corner poles. The packer is kept because it is the only code that knows how to lay out a district and restoring an automatic build is one call — see the district gotchas below for the numbers.
- `company_facilities.lua` — what a company is *given* when it is founded rather than made to shop for: a launch bay. It is given but **not sited** — the company picks its own ground under exactly the rules a public work is held to, via a `"company:<force>"` siting request. Built `owned_by_force` so the company owns it on Nauvis; that flag has to cover the **whole** shape, not just the useful entities — a gate only joins up with walls on its own force, so a half-owned room renders with the gate detached from the wall. The request carries `border = "stone-path"`, so a company's ground is paved and reads as its own. `process()` runs once a second: book whatever was just sited, then put the next queued facility up for placement. Per force, `storage.company_facilities[force] = { queue, sites }`.
- `nauvis_industry.lua` — what Nauvis starts the game owning beyond the compound: the single captured shape `nauvis_start`, built at `START_ORIGIN` (`-14,-55`, the origin it was captured at, which puts its 39x45 box clear north of the compound). It carries the four ore patches and their 16 drills, the red flask line, 12 labs and a solar field with accumulators — **9 substations on one electric network**, so unlike anything sited later it powers itself. It runs a day/night deficit by design. It smelts nothing: the plates its science line runs on have to be sold to Nauvis by players, and its three supply belts are what pull them back out of the warehouse (see the supply-belt gotcha). The warehouse is *not* seeded any more; what Nauvis has to spend on its first expansion is what these drills dig and what players sell it. Also `seal_top_airlock`, and `chart_area`, which derives the charted box from the shape's own clearance box so recapturing a bigger one cannot leave half of it black. Idempotent via `storage.nauvis_industry.built`.
- `item_filter.lua` — allowed items are subgroup `raw-resource`/`raw-material`/`intermediate-product`, non-hidden, and either research-free or craftable by the force's enabled recipes. Cached per player in `player_data.allowed_items`, invalidated on research finish.
- `trading_history.lua` — 60-entry ring buffer per force per item (`storage.trading_history[force][item][slot] = { bought, sold, price }`), plus `storage.trading_chart[force]` (factorio-charts data). `advance_second()` advances `storage.trading_history_head`.
- `market_gui.lua` — persistent Market window (filter All/Pinned/None, search, pin checkboxes, price + trend arrows) and the top-center Credits frame. Buy price displayed is `floor(price * 1.01 + 0.5)`.
- `trading_gui.lua` — Profit & Loss window (shortcut `otc-trading`): three chart panels (income/expense/profit) rendered via `__factorio-charts__.charts` on a dedicated `otc-trading-charts` surface, plus an item list with per-series checkboxes and per-second rates. Per-player state under `player_data.trading_*`.
- `company_gui.lua` — create/join company. Creating gives `STARTING_CREDITS = 5000`. Sets `player.force` to the company force. The **Company tab** carries the company's own siting section (`build_facility_section`) — the same "Choose a site" button as the Nauvis tab's, pointed at the `"company:<force>"` client instead of `"nauvis"`. Opened by selecting the `otc-company-monitor`. The Nauvis tab's warehouse listing is the tradeable set **plus** anything else with stock on hand (science packs, which `item_filter` bans), and `refresh_nauvis_stock` inserts/removes rows in place so the scroll position survives the 60-tick refresh. The Nauvis tab is also the polling station: a Governance section (mayor, your bonds, Buy a bond, Call a mayoral election) and one `build_ballot_section` per open ballot, all rendered by a single renderer keyed on `voting.KINDS`. A ballot opening or closing changes the tab's structure rather than its numbers, so `refresh_nauvis_stock` compares `ballot_signature()` against `player_data.nauvis_ballots_shown` and hands over to a full rebuild when it moves.
- `expand_gui.lua` — expansion shop, opened from a gate computer **in space only**; on `nauvis` it lists nothing, because ground facilities are given (and hand-sited), not bought. The `SHOP` table is the single source of both the listing and the price — add or remove a row and the shop, the Buy button and the purchase check all follow. **Asteroids are deliberately off the list** now that all mining happens on Nauvis: selling a company its own ore patch undercuts the market the game runs on. Their shapes stay captured and registered, so restoring them is one row. Orbital stations are off it too — a company is given one when it is founded. Preview via `platform.show_preview`, buy via `platform.expand_from_gate`. Closes if player walks >6 tiles from the gate.
- `platform_gates.lua` — the 4 starting airlocks (east/west/north/south); `storage.gates["surface:x,y"]` and `storage.gates_by_id[computer_unit_number]`.
- `shape_def.lua` — the shape data format: rotation maths, `transform` (pure, world coordinates), `apply`, `preview`, `clearance_box`, `origin_for_gate`. Canonical orientation is gate-on-west, room extending east; the four compass directions are rotations of the one capture. `DEFAULT_CORRECT_TILES` holds the `set_tiles` correction defaults (`otc-platform` is false, everything else true). A shape's `tile_layers` are also how it says what floor it wants: the district lays grass under every module, and anything harder is the shape's own doing.
- `shape_runs.lua` / `shape_io.lua` — run-length packing for tile lists, and the definition → Lua source serializer shared by the in-game capture and the offline migration harness.
- `shape_capture.lua` — the authoring tool: `/otc-capture-shape <name>`, the selection-tool handler, and `capture_area` which reads a rectangle of world back into a definition. Roles come from `shape_config` tags first, then `ROLE_BY_NAME`; anchors come from `otc-shape-marker` panel text. Admin-only.
- `shape_config.lua` — the other authoring tool: `/otc-config-shape` grants a selection tool that tags entities with a `role`, plus a per-lane item for `role = "supply"`, which `capture_entity` then merges into the definition. `LANE_SIDES` maps transport line index to the screen side it occupies for a given belt facing, so the pickers say "top"/"bottom" rather than "lane 1"/"lane 2" — line 1 is the lane 90° counter-clockwise from travel, so it is top on an east-facing belt and bottom on a west-facing one. Each tag draws a floating label on its entity. Admin-only; both tools are `only-in-cursor` so they cannot reach a player's inventory.
- `shape_registry.lua` — name → definition. Add a line here when you capture a new shape. Also read at the **data stage** by `prototypes/shape_place.lua`, so shape files must stay pure data (`scripts.shape_runs` is their only dependency).
- `shape_place.lua` — the dev placer for shapes that are not bought from a gate: `/otc-place-shape` opens a list, picking one puts a per-shape placement item in the cursor, and left-clicking builds it at the marker's footprint. Admin-only, always placed for the Nauvis force. `on_marker_built` swaps the dummy marker for the real shape; `origin_from_marker` converts the marker's centre back to the shape's top-left origin.
- `room_builder.lua` — shared placement helpers (`place_wall`, `place_gate`, `place_computer`, `register_gate`, `get_surface_force`, `clear_area`), extracted so hooks can use them without requiring `platform.lua`.
- `nauvis_guard.lua` — Nauvis's property is read-only to everyone not in the Nauvis force. Two layers, because most player actions cannot be vetoed, only undone:
  - **Hardened at build time** (`harden_shape`, called from `platform.place_shape`): every Nauvis entity gets `minable = false` and `destructible = false`. This is the only defence against a super-force build (Ctrl+Shift blueprint placement destroys obstructions outright, and nothing can undo that), and it also takes deconstruction planners out of play since only minable entities can be marked.
  - **Undone by event**: GUI opening (which is what stops recipe changes and taking contents by hand), rotation, fast transfer, settings paste (shift+right/left-click), deconstruction and upgrade marks, building anywhere on the nauvis surface, mining, and picking items off the ground.

  `ALWAYS_ALLOWED` exempts the fixtures players are meant to use — gate computer, company monitor, teleporter — because `room_builder.get_surface_force` puts *everything* on Nauvis onto the Nauvis force, so a blanket block would lock players out of expanding and joining companies.
- `platform.lua` — now thin: `expand_from_gate` and `show_preview` resolve a definition, work out origin + rotation, add the connector, apply, and run the hook. `build_shape` places a definition at a fixed position. `place_shape` clears scenery from the footprint first, and `opts.owned_by_force` bypasses the Nauvis force override so a company can own what stands on Nauvis.

## Storage schema (persisted in `storage`)

- `players[player.index]` — `company`, `allowed_items`, `market_filter`, `pinned_items`, `trading_selected_force`, `trading_chart_selection`, `trading_chart_state`, `trading_list_state`, `trading_search_text`, `active_gate`, `selected_shape`, `preview_renderings`; legacy `credits`.
- `companies[force_name] = { credits }` — the balance sheet.
- `station_forces[station_name]`, `rocket_silos[unit_number]`, `otc_teleporters[unit_number]`, `otc_return_teleporters[unit_number] = { surface, position }`, `otc_station_index`.
- `trading_silos[unit_number] = { entity, force_name, buy, sell, circuit }` — `buy` and `sell` are **arrays**, not maps: their order is the player's priority and decides who is served when credits run short. `circuit = { enabled, wire }` where wire is `"green"`, `"red"` or `"both"`.
- `prices`, `supply_demand { tick_counter, period_buys, period_sells, price_offsets }`.
- `stock { items }` — Nauvis's warehouse. Not a Factorio inventory; nothing in the world holds it.
- `supply_belts[unit_number] = { entity, left, right }`, `intake_belts[unit_number] = { entity }`.
- `nauvis_industry { built }`.
- `district { zones, poles, paths, ground, slots }` — `zones[name] = { next, open }` is each zone's next unclaimed module and its part-filled module per size; `poles["x,y"]`, `paths["x,y"]` and `ground["x,y"]` dedupe the power line, its walkway and the grass under a module; `slots` is the built list used for charting a force that arrived late. A save written before zones existed has `taken` or a top-level `next`; `init()` sees either and starts the district over.
- `company_facilities[force_name] = { queue, sites }` — `queue` is the facilities still to be placed and `sites` the list of `{ shape, label, x, y }` already sited. A save from before companies sited their own buildings holds the bare `sites` array; `init()` folds it in.
- `nauvis_siting { requests, holders, completed }` — all three keyed by **client** (`"nauvis"`, `"company:<force>"`). `requests[client] = { client, shape, label, tag, force_name, owned_by_force, sited_by, border }` is the build waiting for a site, `holders[player_index]` is the client whose footprint that player is carrying in their cursor, and `completed[client]` is the finished site handed back once to whoever asked for it. A save with the old single `request` / `holder` / `completed` fields migrates onto the `"nauvis"` client.
- `nauvis_expansion { target, progress, slots, spine_posts, built, awaiting_site }` — `target` is the option currently being funded (set by the ballot); `progress[item]` is goods already taken out of stock and set aside; `slots` is how many district slots are claimed; `spine_posts` is how many substations the spine has laid; `built[key]` counts completions per option. The old rolling `votes` table is cleared on init.
- `voting { ballots }` — `ballots[kind] = { kind, options, votes, start_tick, end_tick, warned }`. `options` is a **frozen** list of `{ key, label, tooltip }` captured when the ballot opened; `votes[player_index]` is an option key.
- `nauvis { minted, burned, holdings, bonds, mayor }` — `bonds[player_index]` is that player's vote weight in every Nauvis ballot; `mayor` is the elected player index, or nil.
- `trading_history`, `trading_history_head`, `trading_chart`, `chart_surface`.
- `gates`, `gates_by_id`.
- `shape_capture { pending }` — per-player pending capture name for `/otc-capture-shape`.
- `nauvis_guard { snapshots, mined, pasted }` — `snapshots[player_index]` is the inventory of the protected entity currently hovered, kept so a fast transfer can be diffed and undone; `mined[player_index]` is the entity about to be mined, kept so it can be rebuilt; `pasted[player_index]` is the destination's settings before a paste, kept so they can be put back.
- `shape_place { selected, clear }` — per-player shape choice for the placer and whether it clears the footprint first (defaults on).
- `shape_config { entities, selection }` — `entities[unit_number] = { entity, role, item_left, item_right, label }` are the in-game role tags; `selection[player_index]` is the entity list the open config window is showing. Entries hold the entity so a mined one can be swept along with its label.

`ensure_company_setup()` in `control.lua` migrates legacy state (player `credits` → "Default" company) and repairs `force_name` on chest entries — extend it when adding migrations.

## Conventions

- 4-space indent. Module pattern: `local M = {}` … `return M`. No comments unless asked.
- Names: prototypes/entities use `otc-` (hyphens); GUI elements use `otc_` (underscores). Loot: `otc_trading_*`, `otc_market_*`, `otc_expand_*`, `otc_company_*`.
- `storage` (never `global`). Lua 5.2 std.
- Suppress spurious diagnostics with `---@diagnostic disable-next-line: undefined-field`.
- Req is `require("scripts.foo")` relative to mod root.
- GUI work: destroy + rebuild list rows rather than mutating when structure changes (see `market_gui.rebuild_market_list`, `trading_gui.rebuild_rows`); factorio-charts chunks must be allocated/freed via `charts.surface.allocate_chunk`/`free_chunk` and render objects destroyed.

## Gotchas

- Buy/sell multipliers live in **two** places: `trading_silo.lua` (execution) and `market_gui.lua` (display). Actual values are 1.01/0.99
- Players join a company via GUI; `player.force` is set to the company force, so a silo's `force_name` is captured at register time and must not be read from the entity afterwards.
- **The trading silo is a `container`, not a `rocket-silo`.** A real silo's input inventory is recipe-filtered to rocket parts and its only cargo path is the rocket, so it cannot be a 100-slot container. `otc-trading-silo` borrows the silo's collision box and sprite fields (`shadow_sprite`, `hole_sprite`, the two doors, `base_day_sprite`) as static `picture` layers, so it reads as a silo and drops into the station shape on the same footprint. There is no launch animation and no power draw until rate limiting exists. `tools/probes/trading_silo.lua` pins the 100 slots, inserter loading, a live buy/sell cycle, and that bots ignore it.
- **It is deliberately not a `logistic-container`.** It was one — `logistic_mode = "storage"`, which does let bots deposit and withdraw — but a logistic chest standing outside any roboport coverage flashes a "not connected to network" alert, and the orbital station has no network. Bot access is meant to come back later; restoring `type = "logistic-container"` plus `logistic_mode` and `max_logistic_slots` is the entire change, and the probe's `want=false` line is what has to flip with it.
- **Only the orbital silo trades.** The launch bay on Nauvis keeps a decorative `rocket-silo`, still registered in `storage.rocket_silos` for the sole purpose of suppressing the vanilla silo GUI.
- **Never take over `player.opened` for the silo.** Doing so removes the vanilla container window, and with it the player's inventory panel, shift-click transfer and filters — none of which can be reproduced by a custom frame. The trading panel is a `player.gui.relative` frame anchored to `defines.relative_gui_type.container_gui` with `name = "otc-trading-silo"`, so it appears to the right of the normal window and closes with it (`on_gui_closed` carries `event.entity`, not an element). `tools/probes/relative_gui_types.lua` lists the anchor enum.
- New surface creation (orbital stations) requires explicit chunk generation and `treat_missing_as_default = false` autoplace settings to stay empty.
- **Inserter `direction` points at the pickup, not the drop.** An inserter facing `east` picks up from the tile to its east and drops to its west. Getting this backwards is silent — the inserter just reports `waiting_for_source_items` forever.
- **A mining drill binds to its ore when it is created.** Build resources before entities or the drill reports `no_minable_resources` forever — rotating it in game is what forces a re-scan. `shape_def.apply` orders it correctly and `test/shape_apply_spec.lua` pins that.
- **An unpaired underground belt works, but only on lines 1 and 2.** `otc-supply-belt` conveys items and inserters can pick off it exactly like a vanilla unpaired underground belt — it is *not* scenery, despite what this file used to claim. What is true is that it reports 4 transport lines and only 1 and 2 are the visible face; 3 and 4 are the buried half, and an item inserted there is stranded forever. `supply_belts.supply_line_count` caps supply at 2 for this reason; intake still drains all 4 so strays are recovered. `tools/probes/supply_belt_lines.lua` pins it. Register either the `otc-supply-belt` itself or a plain `transport-belt` in front of it — both work; the belt itself is usually what you want, because inserters can then take from it directly.
- **A supply belt is only ever an exit (`type = "output"`).** As an entrance it swallows items and plays the wrong animation. `belt_to_ground_type` is **read-only**, and assigning `direction` just flips the type again — they are the same underlying property — so an underground belt cannot be *told* to be an exit, only built as one. `shape_def.create_entity` forces `output` for `otc-supply-belt` regardless of what a capture says, `shape_capture` normalises it on the way out, and `supply_belts.enforce_exit` rebuilds the entity on `on_player_rotated_entity` so a rotation becomes a 180° turn. The rebuild changes `unit_number`, so the supply registration and the `shape_config` tag both migrate — see `shape_config.migrate`. `tools/probes/supply_belt_rotate.lua` pins all of it.
- **A nil lane must stay clear.** `supply_belts.process` picks its item with an `if`, not `cond and data.left or data.right` — that idiom falls through when the left lane is nil and feeds it the right lane's item, quietly filling a lane reserved for an inserter's output.
- **`otc-supply-belt` and `otc-intake-belt` get their role from `ROLE_BY_NAME`.** Each prototype has exactly one purpose, so the config tool only needs to set a supply belt's per-lane items; the role is never worth tagging and a capture cannot lose it.
- **Rotating an underground belt keeps its `unit_number` and its prototype.** It is not swapped for a vanilla belt; only `belt_to_ground_type` and `direction` change. A `shape_config` tag on a hand-built belt survives a rotation — but a *placed* shape's belts are freshly created entities that never had tags, so the config tool showing "(none)" on them is correct, not a bug.
- **There is no API for polling the mouse position.** `cursor_position` exists only on a `CustomInputEvent`, so a hand-drawn preview cannot follow the cursor. `prototypes/shape_place.lua` gets a real hover preview by generating a dummy `simple-entity-with-owner` per shape whose `tile_width`/`tile_height` match its footprint, and letting Factorio draw its own build preview. The dummy sits on its own `collision-layer` (`otc-placement`) that nothing else uses: a **non-empty** mask is what makes the engine draw the footprint highlight at all — an empty one renders nothing and the cursor looks empty — while a layer with no other members still collides with nothing, so placement is never blocked. Clobbering is handled deliberately by `room_builder.clear_area`, not by collision.
- **Placing from the cursor is limited by build reach**, which no shape-sized room can satisfy. `shape_place` raises `force.character_build_distance_bonus` while the tool is held and restores it on placement, on closing the window, and from `on_player_cursor_stack_changed` — the bonus is force-wide, so every exit route has to put it back.
- **Prefix strings used in Lua patterns must be escaped.** `otc-place-marker-` matched nothing until the hyphens became `%-`; the failure is silent, the tool just does nothing.
- **Nauvis is a real world, and everything otc builds clears its own site.** `platform.place_shape` always destroys trees, rocks, cliffs and fish inside the clearance box — that is the "Nauvis clears as needed" rule, and it is separate from `def.clear_area`, which destroys *everything* and is still opt-in per shape. The district lays a grass mix under each module before anything is built on it, and a shape that wants concrete lays it itself in `tile_layers` — the blanket `refined-concrete` slab under every slot is gone. `set_tiles` replaces a water tile outright, so the grass is also what stops a cell landing in a lake (`tools/probes/nauvis_world.lua` pins it).
- **Entity positions in shape definitions are exact centres**, not the sloppy integer tile coordinates `create_entity` will snap for you. `{7, 1}` and `{7.5, 1.5}` place a 1x1 entity identically, but they rotate to different tiles — always store the snapped centre. `test/shape_def_spec.lua` fails on off-grid positions.
- **A rotated shape is a true rotation, not a mirror**, so a room must be an odd number of tiles across its connection axis or its gate sits half a tile off centre and rotating shifts the whole room sideways. The factory was widened from 32 to 33 for exactly this reason. `test/shape_def_spec.lua` asserts every shape stays centred on its gate in all four directions.
- **The district gotchas below describe a packer nothing currently calls.** Fixtures are gone and company facilities are sited by hand, so `district.build` and everything under it is dormant. It is all still true of the code; it is just not what puts buildings on the ground any more.
- **One grid holds everything otc builds on Nauvis** — see `scripts/district.lua`. A **module** is `22 x 20` and a **sub-cell** is a quarter of it, `11 x 10`, sized to the mine block: four mines share a module, and everything larger (flask factory, lab district, solar field, launch bay) takes a whole one. `footprint(def)` reads the fraction straight off the clearance box, capped at a module — a shape too big is given a module anyway and allowed to overhang, because matching the edges exactly was never the point. `origin_for` rounds *down* rather than to nearest, so a shape exactly as wide as its module (the 22-tile flask factory) puts its half-tile of slack inside the cell instead of out over the path.
- **Modules are four to a row, and the two zones grow away from each other.** `ZONES` gives each a starting row and a heading: Nauvis marches **north** from `y = -21`, companies **south** from `y = +21`, so the state's public works and a player's launch bay never queue for the same ground. Each zone counts its own modules, but they share the pole line — both zones start at the same column, and 20 tiles across the compound is inside a big pole's reach, so the whole district is one network.
- **The packer keeps one part-filled module per size per zone, not per shape.** `storage.district.zones.nauvis.open["1x1"]` is where the next mine block goes, so four mines land in one module however many other things are built between them. When the open module fills, the next free one is taken. That is the whole allocator — there is no free-list and nothing is ever released.
- **Power is transmission, not distribution.** The district runs `big-electric-pole` only, four per module, one at each corner. Corner to corner is 24 across and 22 down — inside a big pole's 30-tile wire reach — and every shape's own substation lands inside its 18-tile reach of a corner, so nothing else is needed and no pole ever stands in a room. Neighbours share their corners (deduped by `poles["x,y"]`). **Distribution is the shape's own problem:** every shape that needs power carries its own substation, and the solar field in particular *must* keep the one at its centre, because a big pole's supply area is 4x4 and would leave every panel unconnected.
- **The gutter is two tiles: exactly the path, exactly the pole.** `concrete` fills the whole gap between modules and a 2x2 pole stands on it at each corner, so the path is a readable map of where the power runs. Laid only where a module exists and deduped, so a shared edge is paved once.
- **The ground under a module is a mix of Nauvis's four grasses**, not a slab — `grass_at` picks one per 4x4 patch by integer hash (a float hash could differ between platforms and desync). It goes down before anything is built, which is also what fills a cell that generated as a lake. A shape that wants something harder lays its own floor on top: the flask factory and the lab both do, and the mine blocks deliberately lay nothing so the grass shows through.
- **Every mine block is the stone mine's footprint with different ore under it** (`stone_mine`, `nauvis_mine_iron`, `nauvis_mine_copper`, `nauvis_mine_coal`): four drills onto one belt into an intake, 9x10, no generation of its own. Recapture one and the others have to follow, or the district stops reading as a grid of interchangeable blocks.
- **`shape_capture` does not emit a shape's `hook`.** `shape_io` writes the field when the definition carries it, but `capture_area` builds a fresh definition that never has one, so **every re-capture drops it and it has to be pasted back by hand**. For `nauvis_start` that is `hook = "stock_belts"`, and without it the six intake belts are never registered: the drills run, the belts fill, and not one item reaches the warehouse. Same trap for `nauvis_mine_*`, `stone_mine`, `red_flask_factory` and `nauvis_lab`.
- **`nauvis_start`'s three supply belts are configured in the file, not in game.** `item_left` / `item_right` were worked out from the surrounding inserters and hand-added next to the `hook` line, so a re-capture that has not been tagged with `/otc-config-shape` first drops them and the whole factory stalls with nothing on the bus. What they are, and why:
  - `10.5,37.5` east, the lab feed — `automation-science-pack` on line 1, `logistic-science-pack` on line 2. Both lanes are in use: the top lab row picks straight off this line and the overflow wraps onto the westbound return at `y=38.5` for the bottom row.
  - `26.5,23.5` north, the gear assembler's own one-tile stub — `iron-plate` on line 1, line 2 unused. One lane is provably enough: the gear assembler never reads `item_ingredient_shortage`, only `working` or `low_power`, so its craft speed is the limit and a second iron lane would buy nothing.
  - `25.5,23.5` west, the science line's ingredient bus — `copper-plate` on line 2 and **line 1 deliberately nil**, because the fast inserter at `25.5,22.5` drops the gear assembler's output onto this belt and an inserter always drops on the **far** lane. It stands north of a west-facing belt, so the far lane is the southern one, which is line 1 (`LANE_SIDES[12] = { "bottom", "top" }`). Fill line 1 and the gears have nowhere to go. `tools/probes/nauvis_start_supply.lua` reads the lines back and pins `line1=iron-gear-wheel line2=copper-plate` on the bus.
- **Everything with `direction = 0` in `nauvis_start`'s assembler rows is a *long-handed* inserter, and that is what makes the layout work.** Reach 2 lets it pick out of an assembler and drop **over** the ingredient bus at `y=23.5` onto the return line at `y=24.5`, which runs into the intake. The plain inserters (`direction = 8`) feed off the bus. The one exception is the fast inserter at `25.5,22.5`: reach 1, so its gears land on the bus itself. Swap any of these for the wrong type and items land on the wrong belt with no error.
- **The starting industry is the only thing on Nauvis that powers itself.** `nauvis_start` was captured with its own solar field, accumulators and 9 substations all on one network. Everything sited afterwards is an electrical island (below), so the contrast is deliberate rather than an inconsistency: the opening works, and expanding is what runs into the power problem.
- **Siting lays no power at all, and there is no grid.** It used to put a big pole on each corner of every footprint and refuse any site out of wire reach of an existing one. Both are gone — the poles read as a grid stamped over the landscape, and the reach rule is what forced every new build to huddle against the last. **The consequence is that a sited building is an electrical island:** it has whatever substation its own shape carries and nothing joins it to anything else, so a solar field does not power a mine. Wiring the planet up is unsolved — the options are a player-laid line (they cannot build on Nauvis today; `nauvis_guard` blocks it), poles as a votable public work, or per-building generation. `tools/probes/nauvis_start.lua` pins zero big poles before and after two builds.
- **Nothing Nauvis builds *after the start* generates its own power.** The solar field is the only generation on the ballot. A mine block draws 360 kW and a lab district 720 kW against one field's 1.92 MW — but see above: until the isolation is solved, a sited field only powers what shares its footprint.
- **A company's launch bay is no longer rotated to face spawn.** `district.build`'s `face_towards` did that when the bay was packed into a cell; a hand-sited shape goes down unrotated, so the airlock is always on the west. The player chose the ground, so which wall it opens on is their problem, not the packer's.
- **Gates on Nauvis are decoration.** Nothing is bought from a gate down here any more, so neither `platform_gates.place_gate_controls` nor the `room_gates` hook places a computer when the surface is `nauvis`, and `expand_gui` refuses to list anything there. Players are not sealed in either — they can walk out and explore. The airlock expansion system is alive and unchanged **in space**, off an orbital station's own gates.
- **The orbital station is 21x21 with an airlock in the middle of all four walls.** `station_interior` used to be 15x15 with one gate; it is the room a company lives in until it has bought somewhere else, so it is roomy and opens in every direction. The gate `side` values are the codebase's y-flipped compass (north is `+y`, as in `shape_def.DIR_VECTOR`), which is what lets the plain `room_gates` hook place, pair and register all four — `station_interior.run` is down to the silo and the return teleporter. The concrete and hazard pads are sized to the silo, not the room, so they did not grow with it.
- **`district.build` can rotate a shape in its cell.** `opts.face_towards` is a world position: `facing_steps` turns the shape until its gate is on the wall nearest that position, the axis with the larger delta winning. A rotated shape claims its cell **square** (`claim(def, zone, true)`), because the cell has to hold it either way round.
- **Research and expansion ballots open themselves.** `voting.ensure_standing()` opens one whenever Nauvis has no research current *and* none queued, or no expansion target. That single rule covers game start, a finished technology and a finished expansion, so no caller has to remember to trigger a ballot — and it is also why `nauvis_expansion.build` clears `target` and `research.set_next_research` sets `next`: those fields are the "busy" flags the rule reads.
- **A ballot nobody has voted in is never decided early.** Without that guard a world whose players have not joined yet has zero eligible bonds, so every standing ballot would resolve at random on the first tick. `ensure_standing` also refuses to open anything while `#game.players == 0` — and `game.players` is a `LuaCustomTable`, so `next()` on it errors and only `#` works.
- **Tally the ballot, not the kind, when closing it.** `voting.close` removes the ballot from storage before deciding, so `decide` has to run off the passed-in ballot; going back through `M.tally(kind)` reads nil, scores everything zero and turns every result into a coin toss. `test/voting_spec.lua` pins the plurality, and `tools/probes/voting.lua` pins a whole cycle — real cycle length, a cast vote, an early close and the result actually landing in Nauvis's research queue and expansion target.
- **A ballot's options are frozen when it opens.** The GUI writes its dropdown items once for exactly this reason — the periodic refresh must never move a selection out from under a player mid-click. It is also why the expansion labels can carry a built count: that number only changes when a build finishes, which closes the ballot anyway.
- **A bond's price is progressive, and that is what keeps it honest.** `nauvis.bond_price(player_index)` is `BOND_RATE × total_value() × bonds_already_held`, so reaching *h* bonds costs about `RATE × value × h²/2` — doubling your influence costs four times as much. The multiplier is also the reason buying does not cheapen the next purchase: a purchase burns its price out of the money supply, which shrinks the anchor, but the holder's multiplier climbs faster than the burn shrinks it. A **flat** price off the same anchor walks down a geometric curve instead, and a player can convert their whole balance into an unbounded number of votes. `tools/probes/voting.lua` prints the curve; `test/nauvis_bonds_spec.lua` pins that it only ever rises.
- **`total_value()` uses base prices, not market prices.** Market price moves with scarcity and `supply_demand` offsets, so anchoring governance to it would let someone corner a thin item to crash the bond price and buy influence cheaply. It is the money supply plus Nauvis's warehouse; company assets belong in the sum and join it when `valuation.lua` lands. In practice the warehouse dominates, so a well-supplied Nauvis is one where votes are expensive.
- **The mayor's one power is siting the *state's* works.** `nauvis_siting.can_site` lets the mayor, and only the mayor, place a finished expansion. With the office vacant anyone can, because `voting.ensure_standing` never opens a mayoral ballot by itself, so a world that has not held an election would otherwise never build anything again. A request carrying `sited_by` is a company's own and the mayor has no say in it — that field is the whole difference between the two, and it is checked before the mayor is.
- **A mayor-sited public work gets no border; a company building does.** `border` is per request, so the state's works stand on whatever ground they landed on and a company's are ringed with `stone-path` two tiles deep. The ring lies wholly outside the clearance box, so a shape's own `tile_layers` never fight it, and it goes down *before* the build for the same reason the district lays grass first: it fills a lakeside edge that would otherwise leave a wall standing in water.
- **`nauvis_siting`'s legacy migration keys on `requests` being absent, not on the old fields being present.** `completed` is an empty table rather than nil once converted, and an empty table is truthy, so a check on the old fields alone re-fires the migration on every single `state()` call and silently wipes every open request. `test/nauvis_siting_spec.lua` pins it.
- **The siting tool borrows the dev placer's marker item.** `control.lua` gives `nauvis_siting.on_marker_built` first refusal on `on_built_entity`, before `shape_place.on_marker_built` and before `nauvis_guard.on_built` — which is also what stops the guard mining the marker straight back out of an outsider's hands. It claims a marker only when a request is pending, the builder is the recorded `holder`, and the name matches the requested shape.
- **`max_wire_distance` is a getter in 2.0, not a field.** Quality changes it, so `prototype.max_wire_distance` raises "LuaEntityPrototype doesn't contain key"; it is `prototype.get_max_wire_distance()`. Connection distance is the **shorter** of the two poles' reach. Nothing reads it today — siting dropped its reach rule — but keep this in mind if power ever comes back.
- **A mayor-sited building gets no grass and no path — only poles.** It stands on whatever terrain it landed on (a shape that wants a floor lays its own in `tile_layers`), with a big pole on each of the four corners of its clearance box. Those auto-connect outwards to the pole the site was validated against and inwards to the shape's own substation, so the whole planet stays one electric network. `tools/probes/nauvis_siting.lua` pins that, plus each refusal reason against real terrain.
- Only the east/west/north airlocks exist. The `south` entry (screen-top, gate at `{0,-6}`) was removed from `platform_gates.AIRLOCKS` back when the sealed production room sat against the compound. That room is gone — the flask factory and the lab district replaced it — but `nauvis_industry.seal_top_airlock` still walls the opening off. Note the table's labels are y-flipped relative to Factorio's directions.
